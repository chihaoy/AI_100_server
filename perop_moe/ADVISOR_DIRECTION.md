来源:两次会议(2026-08-28 / 2026-08-29)。
本文只记录**教授说的内容**和它与已有实测的对应关系;执行细节见 `EP_PLAN.txt`,结果见 `README.md`。

---

## 一、问题的重新定义:MoE 本质是 Grouped GEMM

教授带着从 expert 视角重新推了一遍:

```
token 视角:  每个 token 选 top-8
expert 视角: 每个 expert 收到的 token 数【不一样】,且运行时才知道
             每个 expert = 一个 MLP = [token数, H] × [H, I] 的矩阵乘
→ 若干组矩阵乘,每组的"token 数"那一维大小不同
= Grouped GEMM (GMM)
```

**核心问题:怎么把这个"每组形状不同"的 kernel 算快。**

> 教授原话:"你有若干组,每个组内它这一维的 token 数量是都不一样的,它都是变的,
> 然后你现在相当于怎么样在这个上面把这个 kernel 算得很快。"

---

## 二、被明确否掉的一条路:改 padding

- 现状:每个 expert pad 到安全长度,灰色(padding)部分照算
- **MegaBlocks** 已经解决:块稀疏 GEMM,只算深色的真实块
- 教授判断:**"这个问题基本上已经被 solved,现在基本上大家都这么做"**

> **→ 在 QEfficient 里改 padding = 纯 engineering,不是 research**

### MegaBlocks 是什么(arXiv 2211.15841, MLSys 2023)

论文开篇指出的正是我们测到的问题:

> "These formulations force a tradeoff between model quality and hardware efficiency,
> as users must choose between **dropping tokens** from the computation or
> **wasting computation and memory on padding**."

它的解法:
- 把 MoE 表述成**一个块对角的块稀疏矩阵乘**,而不是 128 个独立的稠密矩阵乘
- "allowing for the blocks in the block diagonal matrix to have a **variable number of rows**"
- 块大小 **128×128**(实测最优),padding 只到**块边界**而非容量
  → 每个 expert 浪费上界 ≤127 行(常数),而非 `T` 行
- 自定义 SDD / DSD kernel + BCSR 稀疏元数据(`topology = make_topology(indices)`)
- 结果:**既不丢 token 也不浪费**,比 Tutel 快 40%,比 Megatron-LM 快 2.4x

**为什么搬不到 AI 100**(三条都违反静态形状):
1. 运行时构造稀疏元数据 —— 输出形状随 routing 变
2. 变长的块 —— "variable number of rows"
3. 自定义 CUDA/Triton kernel —— QEfficient 只能通过 ONNX 算子表达

教授对此的判断:**"大概率不太行"**(基于他做手机端 sparse tensor 的经验)。

## 三、研究方向的判据

> **必须是"这个硬件特有、GPU 上没有"的 challenge。**

```
CUDA GPU:  challenge 是在 tensor core 上处理动态 GEMM 尺寸 → MegaBlocks 已解决
AI 100:    计算上大概没什么新东西
           可能新的是 communication —— 计算被切到 64 个小核 / 4 张卡
           粒度比 GPU 的 SM / tensor core 细得多
```

> 教授原话:"pattern 这个事情确实做过,但是在这个硬件上没有人做过,
> 没有人硬件是长成这样子的。"

**先确定有没有独特 challenge;没有就说明这个 topic 没什么好做。**

## 四、三条候选路线

### 路线 ① Profile-guided 静态优化 ← 会上主推

利用 AOT 编译的特点:反正图是提前编好的,那就**提前 profile 学出激活 pattern**:

```
离线 profile 某类 workload
  → 知道每层每个 expert 大概会收到多少 token
  → (a) padding 按需分配:多的多 pad,少的少 pad
  → (b) expert 到卡的分配聪明点,让四卡 balance
       (现在是 e mod 64 轮询,完全不看数据)
```

**两件事可以同时做**——"通过结果推怎么放 expert 和放多少 padding"。

学生质疑"拿结果推过程合法吗",教授回答:**合法,前提是 pattern 不是完全随机**,
他在 coding workload 上确实观察到有 pattern。

### 路线 ② 预编译多张图,运行时选

> "虽然我们的图是 ahead-of-time 编译好、执行时不能变,
> 但是我们可以**同时放好几个 compile graph** 在这个上面,这个没有限制。"

```
按不同的激活 pattern 各编一张图(比如数学一张、代码一张)
→ 请求进来,推断它属于哪种 pattern,挑最合适的图跑
```

- 不同 benchmark 之间 pattern 不同 —— 教授认为**大概率成立**
- 同一 benchmark 内 decode 过程中 pattern 可能漂移 —— **decode 先放着**
- **prefill 一旦 context 定了 pattern 就定了** → 更适合这条路

### 路线 ③ 观察性:细测现有实现

保持现在的 padding 实现不动,细看:
- 每个 core 到底做了什么、分到了什么计算
- **core 与 core 之间需不需要通信**
- **卡与卡之间需不需要通信**

目的是找"这个硬件特有的 challenge"。

**注意**:教授明确说,光测 core 间/卡间通信开销**没用**——
"你测出来这个东西也没有用",必须把它和 MoE 这个问题连起来才有意义。

## 五、方法论

### 研究上
- 先确定有没有独特 challenge,没有就说明题死了
- **不要限死在一条线上**,"你发现它 dead 就真 dead 了,那就做不了"
- 不用跑整个模型,**跑一层 MoE 就行**
- **先看 prefill,decode 先放着**(decode 是另一个问题)
- 碰到困难就想怎么解决,这才是 research

### 用 AI 助手上(教授讲得很具体)
- **只让它做 engineering**
- 它给的结论**要仔细辨别**:"从他做实验得到的 data 到他的 conclusion,内部很多情况是错的"
- **必须让它把实验数据放出来**,没做实验的结论不能信
- 做实验前**心里要有预期**;结果和预期不符时,要仔细查为什么
- 教授举的例子:**"我们一开始想的,有的卡上后面用 padding 也在算,就跟我们想的不太一样"**
- effort 开到最高

## 七、已有实测对这些路线的支撑

截至 2026-08-29 已测出的、可直接作为上述路线输入的数据(详见 `README.md`):

| 会上悬着的问题 | 实测结论 |
|---|---|
| "padding size 到底多少"(教授说不确定) | **pad 到完整 `seq_len`,capacity factor = 16**(= `E/K`) |
| "所有 core 做的事是不是一样的" | ✅ **是**。强制 100% token 压 card0,另外三卡照样 3155 次矩阵乘、922 MB 权重解码,逐位相同 |
| "灰色是不是全算" | ✅ **全算**。而且哨兵索引被钳到 0,读的是 token 0 的**真实数据**,算出真结果再抹掉 |
| "core 间要不要通信" | ✅ `CumSum` 只在 core0(其他核精确为 0),`Einsum_3` core0 是其他核的 12 倍 |
| "卡间要不要通信" | ✅ 每层跨卡归约,`aicbatchedreduceadd` 四卡各 48 次 |
| **①② 的前提:pattern 存不存在** | ✅ **存在且很强** —— 逐层 Gini 0.62,前 10% 的 expert 吃 58.8% 的 token |
| **②的前提:workload 之间 pattern 是否不同** | ✅ **显著不同** —— 逐层 JS 0.325,48/48 层超阈值,top-8 热门 expert 重叠仅 11.2% |
| **① 按需 padding 能省多少** | ✅ 4 档方案(0/16/64/128 行)**省 5.6x**,丢 1.02% token;per-card 容量因子只需 2.04 |
| **① 现在的分配有多不 balance** | ✅ 逐层 max/mean **1.30–1.65**(但当前实现被 padding 抹平,未兑现) |

**路线 ① 的每一个输入都已经量化了。**

### 一个可能是"硬件特有 challenge"的候选

教授要找的"GPU 上没有的问题",有一个很强的候选:

```
EP prefill 核利用率 15.9%,sync HMX 占 94.56%
串行点: CumSum(1/16 核,其他核精确为 0) + Einsum 归约(core0 为主)
```

**cumsum 和 reduce 在 GPU 上有成熟的并行原语**(Blelloch scan、warp shuffle reduce),
而这里被编译器放在了单个核上。**这可能正是"这个硬件特有"的那一条。**

## 九、前置检查结论:MegaBlocks 能不能在 QEfficient/AI 100 上做

日期 2026-09-08。教授会上说"大概率不太行,但你看一看那个 MegaBlocks 能不能写"。

**结论:不行。** 完整报告(含全部证据与复现命令)见 **`MEGABLOCKS_VERDICT.md`**,
那是一份可以单独发出去的文件。这里只留结论骨架:

1. **写不出来** —— QEfficient 的"自定义算子"只是标准 ONNX 算子的组合
   (`CtxGather3D` = `Slice+Shape+Concat+Expand+Unsqueeze+GatherND`),
   递不到硬件 kernel 层;SDK 全部 126 个 `aic*` 算子里矩阵乘只有稠密的
   `aicmatmul`/`aicbatchmatmul`,稀疏算子全是 DLRM embedding 类与空间稀疏卷积;
   MegaBlocks 的块结构由 routing 在运行时构造、块行数可变,AOT 静态形状表达不了。

2. **就算写出来也不省** —— 实测每层平均只有 78.9 个 expert 活跃、
   **每个活跃 expert 仅 7.1 行**,而 MegaBlocks 的块是 128 行。
   块大小 sweep(`tools/moe_blocksize_sweep.py`):

   | 块大小 | GSM8K vs 当前 | HumanEval vs 当前 |
   |---|---:|---:|
   | **MB-128(论文所用)** | **1.62x** | **1.50x** |
   | MB-16 | 11.48x | 9.89x |
   | 理想(无补齐) | 29.32x | 21.61x |

   MB-128 比我们的 4 档静态 padding 方案(5.6x)还差。要让它有效需 T >= 2048。

3. **就算省了也是解错问题** —— EP prefill 实测 `aicconvolutiond32`(真正的矩阵乘)
   只占 **4.3%**,`sync HMX` 占 94.4%,`aiccopytovtcm` 占 14.2%。
   MegaBlocks 的立论前提"padding 浪费 FLOPs"在这台硬件上不成立;
   这里浪费的是**数据搬运与同步**。
   (顺带更正:先前记录的 `blockdequantize_mxfp6` 占 55-70% 有误,实测 7.1-7.8%。)

**对方向的影响**:第 3 点正是教授要的 hardware-specific challenge。
路线 ① 的目标函数应从"减少浮点运算"改写为"**减少 VTCM 搬运量与同步次数**" ——
这是 GPU MoE 文献里没人做、且被这台硬件的成本结构逼出来的题。

## 十、路线取舍:实测判据(2026-09-08)

MegaBlocks 路封死后,对教授给的三条路各自做了数据核对。

### 路线 ①(b) "聪明放 expert 让四卡 balance" —— 我们的数据否掉了

教授设想:现在 `e mod 64` 轮询不看数据,所以卡间不均衡。全 48 层核对:

| | 结果 |
|---|---|
| 按 routing 预测的每卡负载 vs 实测 pcycles 相关性 | **r = -0.024**(192 点) |
| 预测最忙卡与实测最忙卡吻合 | **7/48**(随机期望 12,比瞎猜还差) |
| 实测最忙卡 | card0,**45/48 层** |
| 预测最忙卡 | 四卡均匀轮转(9/11/12/16) |

**实测卡间不均衡不是 routing 造成的,是 core0 的串行工作造成的。**
重排 expert->卡 映射不会让 card0 少做 cumsum。这条路解决的是不存在的问题。

### 路线 ② 多图 —— 判据算出来了,结论比预期微妙

实验:`tools/moe_tier_crossdomain.py`。定长窗口消除两 benchmark 长度差
(HumanEval 中位 119 token vs GSM8K 66),每 benchmark 再切 fit/eval 两半
避免自评乐观偏差。档位 p95。

W=48:

| 分档表来自 | 评估于 | 丢弃率 | 行/层 | vs 当前 |
|---|---|---:|---:|---:|
| gsm8k | gsm8k | **2.20%** | 1188 | 5.17x |
| gsm8k | humaneval | **37.52%** | 1188 | 5.17x |
| humaneval | gsm8k | **33.94%** | 1117 | 5.50x |
| humaneval | humaneval | **3.10%** | 1117 | 5.50x |
| union | gsm8k | 3.08% | 1503 | 4.09x |
| union | humaneval | 2.06% | 1503 | 4.09x |

稳健性:W=64 与 p99 设置下结论不变(域内 0.6-3.1%,跨域 21-38%,差 12-17 倍)。

**结论(需如实向教授说明)**:分档表确实强领域相关,用错表丢 34-38%。
**但 union 表可用** —— 一张通用表 2-3% 丢弃、4.09x。
所以多图**不是必需品而是优化品**:专用图 5.17x vs 通用图 4.09x,多省 26%,
代价是必须能正确分类请求,分错就是 37%。
教授说"prefill 一旦 context 定了 pattern 就定了"正好指向分类可行性
—— 可用 prompt 前几层的路由结果做分类特征。

### 路线 ③ —— 目前最像"硬件特有 challenge"的候选

`CumSum` 只在 core0 执行(其余 15 核精确为 0),而 cumsum 是 MoE 特有的
(把 token->expert 索引打包成紧凑排列)。排除 core0 后核间 max/mean
从 2.39-2.70 掉到 1.08-1.16 —— 核间不均衡几乎全部来自这一个算子。

且 EP prefill op 分解显示:`cumsum` 7.7% > `aicconvolutiond32` 4.3%。
**打包索引比矩阵乘还贵,且只能跑在 1/16 的核上。**
这符合教授"必须和 MoE 连起来"的要求。

### 建议顺序

1. **坐实 ③ 的 cumsum 串行**(判定题活不活,成本最低:补 W 扫描证明串行度不随规模改善)
2. **做 ①(a) 的 ONNX 改写**(主线工程量)
3. **② 作为 ①(a) 的扩展**(分档表已证域相关,多图只是把它参数化)

### 补充:路线 ①(b) 以另一种形式复活

用 GSM8K p95 拟合的分档表(48x128=6144 格,W=48),按现有 `e mod 64` 布局
统计每卡的**档位预算**(= 该卡该层要执行的行数,编译期静态常数):

| | 值 |
|---|---:|
| 48 层加总 max/mean | 1.026(看着很均衡) |
| **逐层 max/mean 均值** | **1.222** |
| 逐层超过 1.15 的层数 | **37/48** |
| 逐层最差 | 1.474 |
| **贪心装箱重排后** | **1.002** |

又一次聚合陷阱:加总 1.026,逐层 1.222。层是串行的,每层等最慢的卡,逐层才作数。

**为什么这个版本活而 routing 版本死**:

| | 死掉的版本 | 复活的版本 |
|---|---|---|
| 均衡什么 | routing 负载(动态预测) | 档位预算(静态常数) |
| 编译期可算 | 否 | **是** |
| 实测验证 | r=-0.024,最忙卡命中 7/48 | 就是图要执行的行数,无需预测 |

**因果链**(重要,现在没有这个不均衡问题):

```
现状:  完全均衡(四卡各 3155 次卷积),但 16x 浪费
分档:  5.17x 节省,但引入 22% 逐层不均衡   <- 分档自己制造的
重排:  编译期贪心装箱 -> 1.002,均衡拿回来,节省保留
```

这解释了教授"两件事可以同时做"的直觉为何正确,但机制不同:
不是两者各解决一部分不均衡,而是**放置在收拾 padding 留下的烂摊子**。

**开放问题**:贪心重排使每层 expert->卡 映射不同。权重本就逐层独立,静态图上合法;
但层间通信模式是否受影响,需查 EP 的 all-reduce 实现。

### 补充 2:路线 ② 可从「N 张图」降级为「1 张图 + N 张置换表」

单层 per-expert 负载统计(`tools/moe_layer_expert_load.py`)发现:

- **48 层里有 25 层存在吃掉 80-92% token 的"独大 expert"** —— 两 benchmark 都有,
  层位置高度重合(12/24/36 两边都独大)
- **但具体是哪个 expert 完全由数据集决定** —— 25 个独大层里只有 4 个指向同一 expert。
  层 12/24/36:GSM8K 是 expert 113,HumanEval 是 expert 98
- 两个 `[48,128]` 负载矩阵整体相关 **r = 0.118**(比 JS 散度更强的跨域发散证据)
- 域内则极稳:split-half 相关 **r = 0.984**(layer 0),全 48 层均值 **0.991**,最小 0.981
  —— 这是教授"pattern 不是完全随机"这一前提的直接证明

据此做的分解实验(`tools/moe_tier_permute.py`,W=48, p95):

| 方案 | 丢弃率 | 行/层 | vs 当前 |
|---|---:|---:|---:|
| HumanEval 自己的表(上限) | 3.10% | 1117 | 5.50x |
| GSM8K 表直接用(跨域) | **37.52%** | 1188 | 5.17x |
| **GSM8K 的形状 + HumanEval 的排名** | **3.75%** | 1188 | 5.17x |

**跨域丢的 37% 不是形状不对,是分给了错的 expert。** 即

```
档位表 = 形状(每层档位多重集)  x  排名(哪个 expert 拿哪一档)
          跨域可复用                 跨域必须重算
```

(形状向量其实并不相同:逐层 L1 距离 180 行,0/48 层完全一致 ——
说明起作用的是"有序预算轮廓"而非精确数值。)

**影响**:路线②不必编 N 张图(每张编译数小时、需单独验证),编 1 张 + N 张置换表即可。

**限制**:换排名 = 换 expert 权重所在槽位 = 权重重排,需重新装载,
只能按部署/按批次切换,做不到逐请求。想运行时切换就得 gather 权重
(每 expert 3 MB),搬运代价爆掉。

### 补充 3:模型自带的周期-12 路由结构(意外发现)

逐层最忙 expert 表(`tools/moe_top_experts_per_layer.py`,输出
`perop_moe/routing/top_experts_per_layer_gsm8k.csv`)显示层 12/24/36 前五名几乎相同,
层 15/27/39 甚至完全相同且同序。量化验证:

**top-16 expert 集合按层间距 d 的重合数(随机期望 2.0):**

| d | 1 | 6 | 11 | **12** | 13 | 23 | **24** |
|---|---:|---:|---:|---:|---:|---:|---:|
| GSM8K | 2.6 | 1.8 | 2.5 | **8.8** | 2.5 | 2.3 | **6.8** |
| HumanEval | 2.0 | 1.5 | 2.1 | **8.7** | 1.8 | 2.1 | **6.8** |

除 12 的倍数外,全部间距都精确等于随机期望 2.0。**两 benchmark 数值几乎相同
-> 模型属性,非数据集属性。**

**机制在 router 权重里**(直接读 checkpoint 的 `mlp.gate.weight [128,2048]`):

```
d=1  +0.4616    d=11 +0.4023    d=23 +0.3408
d=2  +0.4497    d=12 +0.6940 <<< d=24 +0.5269 <<<
d=3  +0.4403    d=13 +0.3922
```

无任何两层共享权重(逐对比较无完全相同),但相隔 12 层的 router 显著更相似。

|---|---:|---:|---:|
| 逐层独立 | 6144 格 | 2.20% | 1188 |
| mod-12 共享 | 1536 格 | **2.35%** | 1614 |

expert->卡 放置——同余类的层或可共用一套放置,减少权重布局种类。待验证。

### 补充 4:分档收益必须区分「行数比例」与「时间比例」(重要修正)

追踪 EP 完整数据流时发现:`[64, T, H]` 里的 `T` 有两种含义,只有一种是 padding。

| 张量 | 中间轴含义 | 分档后 |
|---|---|---|
| `x_chunk` ⑦ / gate,up ⑧⑨ / down ⑪ / mask ⑬ | **打包后第几行** | 变窄 ✓ |
| `expert_out`(累加器) | **第几个 token** | **不变** ✗ |
| ⑮⑯ 归约 `einsum` | **第几个 token** | **不变** ✗ |

代码依据:`matched_idx` 装的是 token 编号,
`expert_out_chunk = gather(expert_out, matched_idx)` 与
`expert_out = scatter(expert_out, matched_idx, ...)` 都用 token 号寻址,
故 `expert_out` 的中间轴必须能索引任意 token,宽度只能是 T。

**收益重算(48 层)**:

| | 现状 | 分档后 |
|---|---|---|
| GEMM ⑧⑨⑪ | 3,711 GMAC | ~554 GMAC(省 85%)✓ |
| `expert_out` | 32 MB/stage | 不变 ✗ |
| 归约(实测 19%) | — | 不变 ✗ |

对照实测时间分布:

```
aicbatchedreduceadd   19.0%   <- 归约, 不受益
aiccopytovtcm         14.2%   <- 部分受益(x_chunk 32MB -> ~5MB)
cumsum                 7.7%   <- 不受益(仍需扫 T)
aicconvolutiond32      4.3%   <- 全额受益
```

**结论:被分档砍掉的 85% 落在只占 4.3% 的那一项上。**
先前报的 5.17x / 6.7x 是**行数比例,不是时间比例**,不能直接当加速比汇报。

**待办**:按张量维度重新归因 profiling 数据,把各 op 分成
(a) 随打包行数缩放 (b) 随 token 数缩放 (c) 固定开销,
才能给出可信的时间加速估计。现有数据够做,需重跑归因。
