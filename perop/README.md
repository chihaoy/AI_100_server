# AI 100 per-op profiling — Qwen3-8B (prefill vs decode)

Per-operator hardware-cycle profiling of Qwen3-8B on the Qualcomm Cloud AI 100, for both
inference regimes, from a single command.

- **Regimes:** `prefill` (`seq_len=128`) and `decode` (`seq_len=1`), both at `ctx_len=256`.
- **Stats are 100% the SDK built-in commands** — `qaic-compile -stats-level=70` → `qaic-runner --aic-profiling-type=raw_device_stats` → `qaic-opstats --summary --trace`. The op-level summary and trace are `qaic-opstats` output verbatim; nothing custom touches the measurement.
- **Optional** per-projection rollup (`q/k/v/o_proj`, `gate/up/down_proj`, `lm_head`) via `ARCH=1` — post-processing that only *sums* the SDK trace's own per-op cycles by node name.

## How to run

**Default — pure SDK stats, both regimes** (random input):

```bash
bash /home/chihao/mllm/research/tools/perop_profile_qwen3.sh
```

**Drive it with your own prompt + get the model's answer** (correctness check):

```bash
PROMPT="what is the capital of china" bash /home/chihao/mllm/research/tools/perop_profile_qwen3.sh
```

**Also emit the optional per-projection rollup** (custom post-processing of the SDK trace):

```bash
ARCH=1 PROMPT="what is the capital of china" bash /home/chihao/mllm/research/tools/perop_profile_qwen3.sh
```

Optional knobs (defaults shown):

```bash
CTX=256 PREFILL_SEQ=128 SAMPLES=4 CORES=16 DEV=0 GEN_LEN=20 \
  bash /home/chihao/mllm/research/tools/perop_profile_qwen3.sh
```

| Var | Default | Meaning |
|---|---|---|
| `PROMPT` | *(unset → random input)* | your prompt; also generates the model's response |
| `TOKEN_IDS` | *(unset)* | raw comma-separated token ids instead of `PROMPT` (skips tokenizer) |
| `ARCH` | *(off)* | `ARCH=1` adds the custom per-projection rollup |
| `CTX` / `PREFILL_SEQ` | `256` / `128` | shape — **forces a recompile** when changed |
| `SAMPLES` | `4` | profiling samples per regime |
| `CORES` / `DEV` | `16` / `0` | NSP cores / card id |
| `GEN_LEN` | `20` | tokens to generate for the response (with `PROMPT`) |

- First run compiles the QPCs (~10 min); re-runs reuse them and go straight to profiling.
- `PROMPT` writes real input buffers (`bindings.json`) into the QPC; unset reverts to random.

## Files needed

Everything the script reads as **input** (nothing here is generated by the run):

### 1. SDK executables — Qualcomm AIC SDK at `/opt/qti-aic/exec`
| Binary | Role |
|---|---|
| `qaic-compile` | ONNX → instrumented QPC (`-stats-level=70`) |
| `qaic-runner` | run the QPC on the card, dump per-op cycle buffers |
| `qaic-opstats` | decode buffers → summary + trace |

The script prepends `/opt/qti-aic/exec` and `/opt/qti-aic/tools` to `PATH`.

### 2. Model — exported ONNX **directory** (`ONNX=`)
Default: `/home/chihao/models/qeff_native_cache/Qwen3ForCausalLM/Qwen3ForCausalLM-d165ffa1b02f89bc/`

> ⚠️ **The `.onnx` file alone is not enough.** `Qwen3ForCausalLM.onnx` is only ~1.7 MB — the
> *graph*. The weights live **beside it as ~500 external tensor files** (`model.embed_tokens.weight`
> 2.4 GB, `onnx__MatMul_*` ~200 MB each, layernorms, `model.{cos,sin}_cached`, …) — the whole
> directory is **~30 GB**. `qaic-compile` reads all of them, so the entire directory must be present.

| File in that dir | What |
|---|---|
| `Qwen3ForCausalLM.onnx` | graph (~1.7 MB) — the path you pass to `ONNX=` |
| `model.*.weight`, `onnx__MatMul_*`, `model.{cos,sin}_cached` | external weights (~30 GB total) |

### 3. Custom-IO descriptor (`CUSTOM_IO=`)
Default `/home/chihao/models/perop_plain/custom_io.yaml` (~8 KB) — tells `qaic-compile` which
I/O tensors stay fp16 etc. Same file works for both regimes.

### 4. The two scripts (in this repo)
| File | Role |
|---|---|
| `tools/perop_profile_qwen3.sh` | the driver you run |
| `tools/perop_by_projection.py` | arch-level aggregator (Python 3, stdlib only) |

### 5. Runtime
- **Python 3** (3.10 tested). The script sources the QEfficient venv `/home/chihao/qeff-venv` if
  present, but only stdlib `python3` is needed for the aggregation step.
- **At least one free AI 100 card** (`DEV=0` by default).

> **No input tensors required.** `qaic-runner` fabricates random inputs (there is no `bindings.json`),
> which is correct for cycle timing. The QPC (`programqpc.bin`), `stats/*.bin`, and `out/` are all
> **produced** by the run — you don't supply them.

  bash /home/chihao/mllm/research/tools/perop_profile_qwen3.sh

| Var | Default | Meaning |
|---|---|---|

| `PREFILL_SEQ` | `128` | tokens processed per prefill step |
| `SAMPLES` | `4` | profiling iterations captured & decoded per regime |
| `CORES` | `16` | NSP cores (tensor-parallel shards) |

## Pipeline (per regime)

```
qaic-compile -stats-level=70        → instrumented QPC (programqpc.bin)
qaic-runner  --aic-profiling-type raw_device_stats  → per-op cycle buffers (*-aiccyclecounts_*.bin)
qaic-opstats --summary --trace      → OP-LEVEL summary.txt + trace.json
perop_by_projection.py              → ARCH-LEVEL per_projection_*.txt/.csv
```

**The input is random, not a real prompt.** `qaic-runner` synthesizes bounded-random tensors
because there is no `bindings.json` in the QPC dir. This is correct for *timing*: per-op cycle
counts are determined by tensor **shapes and the op graph**, not by values. To profile a
different workload, change the **shape** (`PREFILL_SEQ`/`CTX`), not the data.

## Reading the results

### Op level — `op_level_<regime>.summary.txt`
Per-operator-kind table, one block per NSP core (`c0`…`c15`). Columns: `ucycles`, `pcycles`,
`count`, `out KB`, `opdetails`. Percentages **don't sum to 100** — HVX / HMX / DMAIssue engines
run concurrently, so each `%` is against the same total. This file is a byte-for-byte copy of
the first sample in `out/`; the other samples in `out/` differ only by clock jitter (~1 %).

### Arch level — `per_projection_<regime>.txt` / `.csv`
Cycles aggregated per projection (summed over all 16 cores), with each projection's op-kind
split. Answers "which linear costs the most, and is it matmul or weight-dequant?"

> **Note on `o_proj` / `down_proj`:** these have no named MatMul node — the ONNX exporter names
> their matmul after the consuming residual add (`/layers.N/Add` → `o_proj`,
> `/layers.N/Add_1` → `down_proj`). The aggregator remaps them; a tiny residual-add cost rides along.

## Notes

- **Weight-dequant dominates.** In both regimes, `blockdequantize_mxfp6` (unpacking MXFP6 weights)
  is 55–70 % of each projection's cost — more than the matmul itself. Decode is dequant/DMA-bound;
  even prefill stays weight-bound per projection, though attention core (softmax, O(seq²)) grows.
- **Cost is summed across 16 cores** in the arch-level files (weights are tensor-parallel-sharded),
  so absolute pcycles ≈ 16× a single core; the **share %** is the portable number.
- `qaic-opstats` can throw while enumerating a missing sample slot; the script tolerates this and
  proceeds with the samples it decoded (needs ≥1 trace).
- Re-running is cheap: the QPC is reused, so only profile+decode+aggregate rerun.
