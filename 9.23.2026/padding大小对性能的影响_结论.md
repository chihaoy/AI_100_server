# padding 大小对性能的影响 —— 结论整理(2026-09-23)

把 9 月 18 日微基准、9 月 22 日真实 layer 2 容量扫描、9 月 22–23 日 `-mdts-mos=1` 系列三组数据放在一起看。
所有数字都是 4 × Cloud AI 100(每卡 16 核)、SDK 1.21.6 上的实测,Qwen3-30B-A3B,T=128,可追溯到文末列出的目录。

## 一句话结论

**在加了 `-mdts-mos=1` 的正确编译下,T=128 时 padding(每个 expert 的画布行数)对时延没有可测影响。
之前测到的"64 行比 128 行慢、48–96 是坑",是默认编译把 down-projection 按列切成四卡 tensor-parallel 的副作用,不是 padding 本身的性质。**
padding 只在 T ≥ 256(FP16)或 MXFP6 下重新值 5–12%;全 48 层 MXFP6 prefill 尺度上分组和容量都不再带来收益。

## 一、默认编译下:时间不随 padding 单调下降,64 比 128 慢

### 1. 单层微基准(2026-09-18,随机权重,MXFP6,统一宽度扫描)

| 宽度 | 行数(相对 128) | 一层延迟 ms | vs 128 |
|---:|---:|---:|---:|
| 128 | 1.000 | 9.91 | 1.00 |
| 96 | 0.750 | **12.29** | **1.24** |
| 64 | 0.500 | **10.96** | **1.11** |
| 48 | 0.375 | 8.80 | 0.89 |
| 32 | 0.250 | 6.25 | 0.63 |
| 16 | 0.125 | 5.59 | 0.56 |
| 8 | 0.062 | 4.95 | 0.50 |

- 行数减半的 64 行比 128 行慢 11%,96 行慢 24%。
- HMX 按 32 行成块:48 行的 GEMM 周期 = 64 行,24 行 = 32 行。
- 地板约 4.5–5 ms:权重解量化每个 expert 固定约 20.5M 周期,与行数无关。
- 单卡对照:padding 从 128 降到 8 时间不变(3.26 → 3.17 ms)。padding 的代价全在跨卡搬运。
- 换编译选项(`-size-split-granularity=512`、`-ols=2`、`-mos=2`、去掉 `-aic-enable-depth-first`)都修不了 64 行的坑,最多好 6%。

当时的解释:M=128 时编译器把 gate/up 切成 12 段流水,M ≤ 96 时改成 2 段整块,GEMM 周期反而更高;更主要的是 M=64 时编译器把 up-proj 输出也按列切到四卡再 multicast 回来,card0→card1 的 multicast 从 1.87 ms 涨到 3.13 ms。
当时的实践规则:**档位只从 8 / 16 / 32 / 128 里选,避开 48–96。**

### 2. 真实 layer 2 冷组容量扫描(2026-09-22,真实权重与路由,FP16,默认编译)

热组固定 128 行,只扫冷组容量:

| 冷组容量 | 主机延迟 ms(300 次中位) |
|---:|---:|
| 128 | 12.40 |
| 64 | **12.57**(更慢) |
| 32 | **10.56**(最快) |
| 16 | 10.87 |
| 8 | 10.71 |
| 4 | 10.69 |
| 2 | 10.67 |

同一个形状在真模型上复现:64 比 128 慢,32 以下变平,容量 2 时冷组 span 2.15 ms 里 HMX 计算只有 0.04 ms,其余全是依赖等待和传输。
**结论 1 不是测错,在默认编译下它是真的。**

## 二、根因:默认编译把 down-projection 切成了 tensor-parallel

默认编译下 gate/up 是 expert-parallel,但 down-projection 的 `[64, 768, 2048]` 权重被沿 N 切成四份,每卡算所有 64 个 expert 的 512 列输出。
这要求中间激活 all-gather(每轮 36 MiB)和 down 输出 re-shard(每轮 24 MiB),每层跨卡交换 121.6 MiB。

`-mdts-mos=1` 禁止任何权重矩阵跨卡切分,down-projection 只能沿 lane 维分布:每卡 16 个完整 expert,一核一个。

| `-mdts-mos` | 跨卡切了什么 | 每层 P2P | 设备时间 |
|---|---|---:|---:|
| 默认 | down 沿 N 切四份 | 64.0 MiB | 6.59 ms |
| 1 | 不切 | 1.5 MiB | 4.47–4.52 ms |
| 2 | 未观察到切分 | 1.5 MiB | 4.41 ms |
| 4 | gate/up/down 全切四份 | 160.0 MiB | 9.65 ms |

layer 2 重放(`routing_retune/c2_tree`)主机延迟 7.27 → 5.00 ms,输出逐位相同。
把 down MatMul 改写成 Einsum、沿 N 切、按 lane 切、转置权重,都不能改变编译器的决定;只有这个 flag 能。

## 三、加 flag 后:T=128 下 padding 不再影响时延

### 冷组容量扫描(热组 128,FP16,同一会话前后对照)

| 冷组容量 | 默认编译 ms | 加 flag ms | flag / 默认 |
|---:|---:|---:|---:|
| 128 | 12.33 | 7.66 | 0.62 |
| 64 | 12.67 | 7.73 | 0.61 |
| 32 | 10.59 | 7.70 | 0.73 |
| 16 | 10.69 | 7.67 | 0.72 |
| 8 | 10.63 | 7.61 | 0.72 |
| 4 | 10.64 | 7.66 | 0.72 |
| 2 | 10.64 | 7.69 | 0.72 |

### 热组容量扫描(冷组 2)

| 热组容量 | 默认编译 ms | 加 flag ms |
|---:|---:|---:|
| 128 | 10.64 | 7.66 |
| 96 | 11.84 | 7.68 |
| 92 | 11.74 | 7.59 |

两条扫描在 flag 下都是 7.6–7.7 ms 一条平线,差异在轮次间 0.1 ms 的抖动之内。
非 2 的幂的热组容量(96、92)在默认编译下的惩罚(热组 span 4.2 vs 2.8 ms)也消失了。
原因:T=128 时每个 padded GEMM 都藏在权重流之下,临界路径是最忙那张卡上活跃 expert 的权重搬运加稠密归约尾巴,与画布行数无关。

附带发现:加 flag 后,按负载排序的热冷重分组反而比原生 expert 顺序慢 0.7–0.8 ms(默认编译下它值 1.6 ms)。

## 四、padding 什么时候重新起作用

### FP16,更大 chunk(E7,热冷放置,活跃 expert 98 / 110)

| T | 容量 热/冷 | 一层 ms | 每 token µs | vs T/T |
|---:|---:|---:|---:|---:|
| 256 | 256/256 | 6.83 | 26.7 | 1.000 |
| 256 | **158/4**(oracle) | **6.49** | 25.3 | **0.950** |
| 512 | 512/512 | 12.36 | 24.1 | 1.000 |
| 512 | **296/32** | **11.23** | 21.9 | **0.909** |

容量在 T=256 值 5%,T=512 值 9%。down-projection 在预取权重到位后变成 compute-bound,token gather / scatter 随容量增长,padding 才露出来。

### MXFP6(生产精度,E8)

| T | 容量 热/冷 | FP16 ms | MXFP6 ms | MXFP6 vs 其 T/T |
|---:|---:|---:|---:|---:|
| 128 | 128/128 | 3.93 | 2.85 | 1.000 |
| 128 | 92/2(oracle) | 3.90 | **2.60** | **0.912** |
| 256 | 256/256 | 6.77 | 5.91 | 1.000 |
| 256 | 158/4(oracle) | 6.51 | **5.20** | **0.879** |
| 512 | 512/512 | 12.31 | 11.35 | 1.000 |
| 512 | 296/32 | 11.29 | **9.92** | **0.875** |

MXFP6 下权重字节缩 2.6×,权重流不再是瓶颈,padding 从 T=128 起就值 9–12%。
但 MXFP6 的每 token 成本不随 T 下降(20.3 / 20.3 / 19.4 µs),因为 token 数成比例的累加/combine 路径暴露出来了。
不加 flag 的 MXFP6 图慢 1.14–1.99×,flag 与精度无关,始终必要。

### 全 48 层 MXFP6 prefill(E9–E12)

| 版本 | 主机延迟 ms |
|---|---:|
| 生产基线(默认编译) | 497 |
| 只加 `-mdts-mos=1` | 352 |
| + 移植 layer 2 的层级重写到全部层 | 243 |
| + token-centric combine(去掉稠密累加器) | 232 |

logits 与历史逐位相同。**这个尺度上分组和容量都不再带来收益**,静态热冷重分组反而有害;剩下的瓶颈是 token 数成比例的 combine 路径。
限制:flag 会破坏 KV retained state 的输入输出配对,全模型 flag 版本目前是 prefill-only。
